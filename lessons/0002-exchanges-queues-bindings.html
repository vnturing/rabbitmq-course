How an exchange picks the queue

Your win: given a message's routing key and a set of bindings, work out which queues receive it, and say when you would choose fanout, direct or topic.
Warm-up from Lesson 1 (answer aloud first)

Name the four nouns, say where a publisher sends a message, and say what a binding is. Check: publisher, exchange, queue, consumer; publishers send to an exchange; a binding is the rule that links an exchange to a queue.

1. The open question

Last time the exchange had bindings to a fulfilment queue and an email queue, but we never said how it chose. Now the shop has three queues: email, warehouse and analytics. When "order placed" arrives, which ones get it? Two inputs decide.

  • The message carries a routing key, a label such as order.placed, set by the publisher.
  • Each queue's binding can carry a binding key. The routing key acts like a filter against it (RabbitMQ: AMQP 0-9-1 Model Explained).

The exchange type is the matching rule that compares them. RabbitMQ provides four types: direct, fanout, topic and headers (same guide). We take the first three, simplest first.

2. Fanout: everyone gets everything

A fanout exchange ignores the routing key and delivers a copy to every bound queue. If N queues are bound, N copies go out (guide). Use it for broadcast: every consumer wants every event.

3. Direct: exact match

A direct exchange delivers to queues whose binding key equals the message's routing key. If several queues share the same binding key, all of them receive the message (guide). Use it when each message has one clear kind, such as payment versus refund.

4. Topic: match on patterns

A topic exchange matches the routing key against the pattern used to bind each queue. Routing keys are words separated by dots, and two wildcards are allowed in binding keys: * stands for exactly one word and # for zero or more words (RabbitMQ tutorial 5: Topics). Using <thing>.<event> keys, the three queues above behave like this:

Message routing keyemail order.*warehouse order.placed, stock.*analytics #
order.placedyesyesyes
order.cancelledyesnoyes
stock.lownoyesyes
order.placed.euno (three words)noyes

Three facts from the tutorial worth remembering. A queue bound with just # receives everything, like fanout. Without wildcards, a topic exchange behaves like a direct one. And a message that matches two bindings of the same queue is delivered to that queue once (tutorial 5). A message matching no binding is lost unless the publisher asked for it to be returned (see Lesson 1 and Publishers).

The fourth type, headers, routes on message headers and ignores the routing key. You will rarely need it for this course.

Which of these your target company actually meets depends on what exchange Laravel's RabbitMQ driver publishes to. We check that in Lesson 3 instead of guessing.

5. Practice: answer from memory

6. Say it out loud

Interview prompt: "When would you use a topic exchange instead of fanout?"

Model answer

"Fanout sends every message to every bound queue, which is right when all consumers want everything. A topic exchange lets each consumer subscribe by pattern on the routing key, so email can take order.*, the warehouse can take stock events, and analytics can take #. The RabbitMQ docs recommend considering topic exchanges whenever several consumers selectively choose which kinds of messages they want."
