Running workers in production

Your win: explain how queue workers are kept alive, deployed, recycled and sized, and spot the mistakes in a Supervisor config.
Warm-up from Lesson 5 (answer aloud first)

Which worker setting must be shorter than retry_after, and why? Check: --timeout; otherwise a job may be re-attempted before it finishes and processed twice (documented for Laravel's built-in drivers).

1. A worker is a long-lived process

So far a "worker" was a box in a diagram. In reality queue:work is a PHP process that boots your application once and then keeps running, holding that booted state in memory. Two consequences, both from the Laravel docs:

  • It does not notice code changes after it starts, so deployments must restart workers.
  • Static state your code creates is not reset between jobs, and daemon workers do not reboot the framework per job, so heavy resources should be released after each job.

Everything else in this lesson follows from those two facts.

2. Keeping workers alive: a process monitor

The command keeps running until it is stopped, and it will stop: after a worker timeout, after queue:restart, or on a crash. So production needs a process monitor that restarts it. The Laravel docs use Supervisor for this and run several processes with numprocs (Supervisor Configuration).

[program:laravel-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /home/forge/app.com/artisan queue:work --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
numprocs=8
stopwaitsecs=3600

This is the docs' example. The docs warn that stopwaitsecs must be greater than the seconds taken by your longest-running job, or Supervisor may kill a job mid-run.

3. Deploying: restart gracefully

new code"] --> B["php artisan
queue:restart"] --> C["Workers finish the

restarts them"] --> E["Workers boot
with new code"]

queue:restart tells all workers to exit gracefully after their current job, so no in-flight job is lost. It relies on the cache to store the restart signal, so a cache driver must be configured (Queue Workers and Deployment). Likewise, when a worker receives SIGTERM, SIGINT or SIGQUIT mid-job, it finishes the job before exiting. A job can implement Interruptible to react to the signal, for example to save progress (Reacting to Worker Signals).

4. Recycling workers on purpose

Because memory accumulates in a long-lived process, the docs offer limits that make a worker exit so the process monitor can start a fresh one (The queue:work Command):

  • --max-jobs=1000: exit after that many jobs.
  • --max-time=3600: exit after that many seconds.
  • --memory=60%: exit above a memory limit (default 128 MB; percentages need a finite PHP memory_limit).

Concurrency comes from running more processes: numprocs in Supervisor, or several queue:work commands. Priority comes from listing queues, as in --queue=high,low, which drains high first.

5. The RabbitMQ side: prefetch

Prefetch (the basic.qos setting) limits how many unacknowledged messages a consumer may hold at once. In RabbitMQ it applies separately to each consumer on a channel, and a value of 0 means no limit. A server-wide default can be set with default_consumer_prefetch (RabbitMQ: Consumer Prefetch). It concerns consuming with acknowledgements, which ties back to Lesson 4. I could not verify how the Laravel driver sets prefetch, so make that a question for the team rather than an assumption.

Two things from Lesson 3 combine here. rabbitmq:consume handles one queue, so reproducing --queue=high,low priority behaviour would mean separate worker processes per queue (my reading of that limitation). And Laravel's docs describe Horizon as a dashboard for Redis-powered queues, while the driver's README says it supports Horizon via RABBITMQ_WORKER=horizon, so ask whether they use it.

6. Practice A: spot the mistakes

[program:shop-worker]
command=php /var/www/shop/artisan queue:work --timeout=300 --tries=3
numprocs=4
autorestart=false
stopwaitsecs=10

List what would go wrong in production, then open the answers.

Answers
  1. autorestart=false: after a timeout or queue:restart the worker exits and nothing starts it again, so the queue silently stops being processed.
  2. stopwaitsecs=10: jobs allowed to run up to 300 seconds can be killed mid-run when Supervisor stops the process. It should exceed the longest job.
  3. No --max-time, --max-jobs or --memory tuning: nothing recycles the process as memory accumulates.
  4. Nothing here restarts workers on deploy: the release process needs php artisan queue:restart.

7. Practice B: answer from memory

8. Say it out loud

Interview prompt: "Walk me through deploying new code to an app with queue workers."

Model answer

"Workers are long-lived processes that keep the old code in memory, so after the release I run queue:restart. Workers finish their current job and exit, and Supervisor starts them again on the new code. That depends on a configured cache for the restart signal, on Supervisor's stopwaitsecs being longer than my longest job, and on jobs being safe to repeat in case one is interrupted."

Ask the team

  1. What runs the workers (Supervisor, containers, Horizon), and how many per queue?
  2. Which consume command do they use, and what prefetch is set?
  3. How does a deploy restart workers?
  4. How do you monitor queue depth and failed jobs? (Laravel also has a "Monitoring Your Queues" section worth reading.)
