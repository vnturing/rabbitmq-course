When jobs fail (and when they run twice)

Your win: trace what happens to a failing job in Laravel and in RabbitMQ, and make an order-fulfilment job safe to run twice.
Warm-up from Lesson 4 (answer aloud first)

A worker dies mid-job and never acknowledges. What does RabbitMQ do, and what side effect follows? Check: it redelivers the message to another consumer, so the job can run twice.

1. Two reasons the same job runs again

There are two separate mechanisms, and an interviewer may test whether you can tell them apart.

  • Laravel retries: the job threw an exception or timed out, and Laravel attempts it again.
  • RabbitMQ redelivery: the consumer never acknowledged, so the broker hands the message to someone else (Lesson 4).

Either way, the same job body can execute more than once. A job is idempotent when running it twice has the same effect as running it once. That is my summary of the two mechanisms; the term itself is explained well in Stripe's docs on safely retrying requests (Stripe: Idempotent requests).

2. Laravel's failure pipeline

Facts from the Laravel 13 queue docs:

  • By default, Laravel attempts a job once. Raise it with --tries on the worker or with the Tries attribute (or a tries() method) on the job.
  • An attempt is consumed by an unhandled exception, a manual release, a middleware release, a timeout, or a normal completion.
  • Backoff sets the delay between retries. An array such as [1, 5, 10] waits 1 second, then 5, then 10, and 10 for every later retry.
  • When attempts run out, the job goes into the failed_jobs table and its failed() method is called. Inspect with queue:failed, retry with queue:retry <id> or queue:retry all.

Jobs run with dispatchSync are not stored in failed_jobs; their exceptions are handled immediately (same docs, "Dealing With Failed Jobs").

3. The timeout trap

The worker's --timeout (60 seconds by default) must be several seconds shorter than the connection's retry_after value. Otherwise a job can be re-attempted before it has finished, and processed twice (Laravel: Job Expirations and Timeouts). Timeouts also need the PCNTL PHP extension.

Careful: retry_after is documented for Laravel's built-in drivers. The RabbitMQ driver's README does not mention it, so do not assume it applies; in RabbitMQ, redelivery is driven by acknowledgements (Lesson 4). The README does suggest ext-pcntl for all consumer features (README).

4. The RabbitMQ side: dead letters

Laravel's failed_jobs table lives in your database. RabbitMQ has its own mechanism: a queue can name a dead letter exchange, and messages are republished there when they are rejected without requeue, expire, overflow a length limit, or exceed a quorum queue's delivery limit. Dead letter exchanges are ordinary exchanges. If the target queue is missing, the messages are silently dropped, and by default the republish does not use publisher confirms, so it is not guaranteed safe in a cluster (RabbitMQ: Dead Letter Exchanges).

The driver bridges the two worlds with reroute_failed: Laravel still stores failed jobs in the database, but the message can also be sent to a failed exchange. If you set no failed routing key, it defaults to the queue name plus .failed, and you probably create that exchange and queue yourself (README). Whether your target company uses either mechanism is a good question.

5. Making a job safe to run twice

Three tools, in order of how often people confuse them:

  • Idempotency key on external calls. Stripe's API saves the result of the first request made with a given key and returns it for retries. All POST requests accept a key, and Stripe suggests random V4 UUIDs (Stripe docs). Whether a warehouse API supports this is something to find out.
  • ShouldBeUnique. A unique job is not dispatched while another instance is on the queue and unfinished. It needs a cache driver with atomic locks shared by all servers, and does not apply inside batches (Laravel: Unique Jobs). It stops duplicate dispatch. It does not stop a retried or redelivered job from running again.
  • WithoutOverlapping. Prevents two jobs with the same key from processing at once, and a released job still consumes an attempt (Laravel: Preventing Job Overlaps).

Beyond those, a common pattern (mine, not from these docs) is for the job to check the record's own state first and record each side effect when it is done.

6. Practice A: make it safe

public function handle(Warehouse $warehouse, Mailer $mail): void
{
    $this->order->product->decrement('stock');   // 1
    $warehouse->createShipment($this->order);     // 2
    $mail->sendReceipt($this->order);             // 3
}

The worker crashes after step 2 and the message is redelivered. What happens on the second run, and what would you change?

Answer

All three steps run again: stock is decremented twice, a second shipment is created, and a second receipt goes out. Fixes: skip work already recorded on the order (for example a shipped marker checked at the top of handle()), set each marker as soon as its step succeeds, and pass a stable idempotency key to the warehouse call if that API supports one. Keeping each side effect in its own small job also limits what a retry repeats.

7. Practice B: answer from memory

8. Say it out loud

Interview prompt: "What does idempotent mean, and why does it matter with queues?"

Model answer

"Idempotent means running something twice has the same effect as once. With queues a job can run more than once: Laravel retries after an exception, and RabbitMQ redelivers if a worker dies before acknowledging. So side effects like charging, shipping and emailing need guards: state checks on the record, idempotency keys on external APIs such as Stripe, and unique-job locks only to prevent duplicate dispatch, which is a different problem."

Ask the team

  1. What are your default tries and backoff, and who gets alerted when jobs land in failed_jobs?
  2. Do you use dead letter exchanges or the driver's reroute_failed?
  3. How do you make fulfilment and email jobs safe to repeat?
