RabbitMQ in Laravel · Lesson 1 · about 12 minutes

Why a checkout needs a queue

Your win: look at an order-placed flow, say which steps stay in the web request and which move behind a queue, and trace one message from Laravel to a worker using the four RabbitMQ nouns.

1. The problem: a checkout that does everything

Imagine the electronics shop's "Pay" button. Behind it, the app has to do a lot of things. Done one after another inside the web request, the customer waits for all of them.

The dashed steps depend on other services (a mail provider, a warehouse API) that can be slow or down. Laravel's own documentation describes exactly this situation: tasks that take too long for a normal web request are moved to a queue so the application can respond quickly (Laravel: Queues).

The customer needs to know one thing before the confirmation page: did my payment work? The receipt, the warehouse sync and the analytics can happen a few seconds later. That is usually where the line is drawn, though it is a design decision, not a law.

2. The idea: leave a note, let someone else do it

A queue is a to-do list sitting between two programs. The web request writes a note ("fulfil order 1042") and returns immediately. A separate long-running program, a worker, picks notes up and does the slow work.

flowchart LR
  W["Web request
(Laravel)"] -- "writes a note" --> Q[["Queue"]] -- "picked up later" --> K["Worker
(separate process)"]

In Laravel the note is a job class. Dispatching it puts it on a queue; a worker started with php artisan queue:work runs it (Laravel: Queues).

// in the checkout controller, after payment succeeds
$order = Order::create([...]);

FulfilOrder::dispatch($order)->onQueue('fulfilment');

return redirect()->route('orders.thanks', $order);

// app/Jobs/FulfilOrder.php
class FulfilOrder implements ShouldQueue
{
    use Queueable;
    public function __construct(public Order $order) {}
    public function handle(WarehouseClient $warehouse): void { /* email, stock sync */ }
}

When a job takes an Eloquent model, only the model's identifier is serialized onto the queue; the worker re-fetches the model when it runs (Laravel docs). So the note says "order 1042", not a copy of the order.

3. Enter RabbitMQ: who holds the notes?

Something has to store the notes safely between the web request and the worker. Laravel can use a database table or Redis for this. This company uses RabbitMQ, a message broker: a server whose whole job is to accept messages, route them and hold them until a worker takes them. It has four nouns. We add them one at a time.

NounPlain meaningIn the shop
PublisherProgram that sends a messageThe Laravel web app, at checkout
ExchangeWhere messages arrive; it decides where they goA router for order events
QueueHolds messages until someone takes themOne per kind of work, e.g. fulfilment
ConsumerProgram that receives and handles a messageThe Laravel worker

The surprising one is the exchange. A publisher does not put messages straight into a queue. In the AMQP 0-9-1 model RabbitMQ uses, messages are published to exchanges, and exchanges distribute copies to queues using rules called bindings (RabbitMQ: AMQP 0-9-1 Model Explained). A binding is the rule that says "this queue wants messages from this exchange".

  P["Publisher
Laravel web app"] -- "order placed" --> X{{"Exchange"}}
  X -- "binding" --> Q1[["fulfilment queue"]]
  X -- "binding" --> Q2[["email queue"]]
  Q1 --> C1["Fulfilment worker"]
  Q2 --> C2["Email worker"]

Which queues receive a message depends on the exchange type and the bindings; that is Lesson 2. If a message matches no queue at all, it is either dropped or returned to the publisher, depending on options the publisher set (same guide).

One wrinkle you may meet: it can look like you publish straight to a queue. RabbitMQ has a nameless default exchange; every declared queue is automatically bound to it using the queue's name as the routing key. So publishing "to a queue" is really publishing through that exchange (RabbitMQ: Exchanges).

4. Where Laravel fits

A community-maintained driver, vladimir-yuldashev/laravel-queue-rabbitmq, lets Laravel use RabbitMQ as a queue connection. Its README says that once configured you use Laravel's normal queue API, so the dispatch() call above does not change. Exactly which exchange and routing key it uses by default is something we will check in the driver's documentation in Lesson 3 rather than assume. I cannot tell from here whether your target company uses this driver or another one; that is a good interview question.

6. Say it out loud

Interview prompt: "Why would an e-commerce site put order processing behind a message queue?" Answer in 30 seconds, using the words publisher, exchange, queue and consumer, then open the model answer.

Model answer

"Checkout should only wait for what the customer needs to know, whether the payment worked. Receipts, stock sync and analytics depend on other services and can be slow or fail, so the app publishes a message and returns. RabbitMQ takes the message at an exchange, routes it by bindings into queues, and workers consume from those queues at their own pace. That keeps the checkout fast and means a slow warehouse API does not stall a customer."

Primary source

Read the opening sections of AMQP 0-9-1 Model Explained on rabbitmq.com, up to and including bindings. It is the official explanation of the nouns used here.
