A queue is bound to a topic exchange with order.*. Does order.placed.eu reach it? Check: no. * matches exactly one word, and that key has three.

1. Which driver? A caveat first

Laravel ships drivers for the database, Redis, SQS and others, but not RabbitMQ (Laravel: Queues). The common community package is vladimir-yuldashev/laravel-queue-rabbitmq. Its page lists v15.0.2 (September 2026), requiring Laravel 10 to 13 and php-amqplib. I do not know that your target company uses it, so treat everything below as "what this driver does" and confirm with them.

The package's own promise: once configured, you use the normal Laravel Queue API and change nothing else in your job code (README). That is why your FulfilOrder::dispatch(...) from Lesson 1 stays the same.

3. Where does the message go? The exchange options

The README documents optional exchange, exchange_type and exchange_routing_key settings under options.queue. Its rules, in its own terms:

  • If you set an exchange but no routing key, the routing key is the queue name.
  • If the exchange is omitted while using these routing-key options, RabbitMQ uses amq.direct.
  • If you publish to an exchange with a routing key, you probably create the queues and bindings yourself.

That last line is Lesson 2 showing up in production: someone has to declare the bindings that connect the exchange to the queues. The README does not spell out what happens when you set no exchange options at all, so I will not guess. On a real system you can see it directly in the RabbitMQ management interface, under exchanges and queues.

4. How do workers consume? Two commands

The README describes two ways (Consuming Messages):

  1. queue:work, Laravel's built-in command. It uses basic_get and can consume multiple queues.
  2. rabbitmq:consume, from the package. It uses basic_consume, is described as about twice as performant, but does not support multiple queues.

Connect this to Lesson 2's source: RabbitMQ's guide calls subscribing ("push") the recommended way to consume and polling ("pull") highly inefficient in most cases (AMQP 0-9-1 Model Explained). Which command the company runs is a good, specific question to ask.

5. Three more options worth recognising

  • Horizon: set RABBITMQ_WORKER to horizon to use Laravel Horizon with this driver (README).
  • Foreign messages: if another application publishes messages that do not follow Laravel's job payload, you can extend the package's RabbitMQJob class and point the job option at yours (README). This is the clue that RabbitMQ is often shared between services, not just between Laravel and itself.
  • Teasers: after_commit (Lesson 4) and reroute_failed (Lesson 5).

6. Practice A: read the config

This sample is illustrative, built from the README's option names. Answer each question aloud, then open the answers.

'rabbitmq' => [
    'driver' => 'rabbitmq',
    'hosts'  => [['host' => env('RABBITMQ_HOST'), 'port' => 5672, 'vhost' => 'shop']],
    'queue'  => 'fulfilment',
    'after_commit' => true,
    'options' => ['queue' => [
        'exchange' => 'shop-events',
        'exchange_type' => 'topic',
        'reroute_failed' => true,
        'failed_exchange' => 'shop-failed',
    ]],
],
  1. A job is dispatched with no onQueue(). Which queue?
  2. Which exchange does it publish to, and with what routing key?
  3. Who has to make sure the fulfilment queue actually receives it?
  4. A job fails for good. Where does a record of it end up?
Answers
  1. fulfilment, because queue sets the connection's default queue.
  2. The shop-events topic exchange, with routing key fulfilment (the queue name, since no routing key is set).
  3. Whoever manages the topology: the queue needs a binding on shop-events whose key matches fulfilment. The README says you probably create these bindings yourself.
  4. Laravel stores failed jobs in the database; with reroute_failed the message is also rerouted to the shop-failed exchange (README). Lesson 5 covers this properly.

7. Practice B: answer from memory

8. Questions to ask the team

  1. Which RabbitMQ driver and version do you use, and do workers run queue:work or rabbitmq:consume?
  2. Do you publish to the default setup or to your own exchange, and who declares the bindings?
  3. Do other services publish into the same broker?
