1. A message crosses four hand-offs

An order is only safe if nothing is lost or half-done at any hand-off on its way. Each hand-off has its own failure and its own safeguard. We take them in order.

2. Hand-off 1: the database and the dispatch

Dispatching a job inside a database transaction is allowed, but a worker can pick the job up before the transaction commits, so the rows it needs may not exist yet (Laravel: Jobs & Database Transactions). The reverse also bites: the transaction rolls back but the job already went out.

Laravel's fix is the after_commit connection option. When it is true, a dispatch inside a transaction waits until the open parent transactions commit, is sent immediately if none are open, and is discarded if the transaction rolls back. You can also choose per dispatch with ->afterCommit() or ->beforeCommit(). Setting the option also affects queued listeners, mailables, notifications and broadcast events (same section). The RabbitMQ driver's README shows the same after_commit key on its connection (README).

DB::transaction(function () use ($cart) {
    $order = Order::create([...]);
    FulfilOrder::dispatch($order)->afterCommit(); // sent only if the transaction commits
});

3. Hand-off 2: Laravel to the broker

Did RabbitMQ actually take the message? Publisher confirms are the broker's acknowledgements back to the publisher; consumer acknowledgements are a separate feature and the two are unaware of each other (RabbitMQ: Acknowledgements and Confirms). Also remember Lesson 1: a message that matches no binding is dropped or returned, depending on what the publisher asked for, and RabbitMQ exposes metrics that help spot publishers sending unroutable messages (Publishers).

4. Hand-off 3: surviving a broker restart

Two settings are needed together. The queue must be durable, and the publisher must mark each message persistent. Publishing to a durable queue does not by itself make a message persistent, and persistence costs some performance (AMQP 0-9-1 Model Explained).

5. Hand-off 4: worker to broker

With manual acknowledgements, RabbitMQ removes a message from the queue only after the consumer acknowledges it. If the consumer dies first, the message is redelivered to another consumer, or held until one registers (guide). With automatic acknowledgement, the message counts as delivered the moment it is sent, so a connection that drops before processing loses it; the docs call this mode unsafe for many workloads (confirms guide). Note the side effect: redelivery means a job can run twice. That is the subject of Lesson 5.

The acknowledgement mode is chosen when a consumer subscribes with basic.consume or fetches with basic.get (same guide). Those are the two methods behind Lesson 3's two commands.

6. What the driver documents, and what it does not

The driver's README documents after_commit, but I could not find its defaults for queue durability, message persistence, publisher confirms or acknowledgements there. Do not assume them. On a real system the RabbitMQ management interface shows each queue's properties, and these are good questions for the team (see the end).

7. Practice: match the incident to the fix

8. Say it out loud

Interview prompt: "How do you make sure an order is never lost between checkout and the warehouse?" Walk the four hand-offs, then open the model answer.

Model answer

"I think in hand-offs. First, dispatch after the database commit, using Laravel's after_commit, so a rollback never leaves a stray job and a worker never races the transaction. Second, use publisher confirms so the app knows RabbitMQ accepted the message. Third, durable queues plus persistent messages so a broker restart does not wipe them. Fourth, manual acknowledgements so a crashed worker's message is redelivered. The price of that last one is that jobs can run twice, so the jobs themselves must be safe to repeat."

Ask the team

  1. Are your queues durable and messages persistent, and do you use publisher confirms?
  2. Is after_commit set on the connection, or do you call afterCommit() per dispatch?
  3. What happens to a job if a worker is killed mid-run?
